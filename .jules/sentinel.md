## 2024-06-21 - [Open Redirect via Unverified window.location.href Assignments]
**Vulnerability:** Open Redirect and SSRF risks from assigning unverified user-controlled inputs (like redirect URIs) directly to `window.location.href`. The URL validator was also using `.includes()` instead of strict Regex for domain validation, making it vulnerable to subdomains like `evzone.com.attacker.com`.
**Learning:** Using React's internal routing (e.g., `navigate()`) does not protect against external URL schemes if the application manually assigns parameters to `window.location.href`. Malicious inputs can lead to Open Redirects, and `new URL()` alone doesn't prevent this if the domain validation logic is flawed.
**Prevention:** Always strictly validate dynamic URLs against an allowed list of domains using exact matches (`===`) or strict Regex (e.g., `/^([a-z0-9-]+\.)*(evzone\.com|evzone\.app|evzonemarketplace\.com)$/i`) before assigning to `window.location.href`. Use a fallback to internal routing (`navigate('/app')`) if the validation fails.

## 2024-06-21 - [Relative URL Parsing Regression]
**Vulnerability:** Not a direct vulnerability, but a critical security-patch regression where overly strict URL validation (intended to prevent SSRF/Open Redirects) inadvertently broke legitimate client-side relative routing by failing to accommodate relative paths when parsing with `new URL()`.
**Learning:** In JavaScript, executing `new URL("/dashboard")` without providing a base origin throws a `TypeError`. If a validation utility (`isValidUrl`) catches all parsing errors to return `false` as a security fallback, it will reject all valid relative paths in addition to malicious payloads, breaking core application routing.
**Prevention:** When patching Open Redirects, explicitly evaluate if relative routes are expected. If they are, incorporate safe relative path validation (e.g., `url.startsWith('/') && !url.startsWith('//')`) directly within the URL sanitizer to prevent breaking client-side logic.
